# HEALTH-01 — Диагностика синхронизации Apple Health

## 1. Симптом и дата наблюдения

Исходная формулировка (CONTEXT.md D-01): синхронизация HealthKit срабатывает один раз, затем «замирает» — новые данные из Apple Health в последующие дни/сессии не подтягиваются в приложение.

Снятая до начала диагностики гипотеза (D-02): разрешение HealthKit было подтверждённо выдано пользователем через экран настроек (`health.tsx`), флаг `healthkit_connected` в SecureStore установлен — причина НЕ в отсутствующем разрешении.

Тип сборки: **dev** (`npm run ios`, `TerenAIDev.app`, Debug-iphoneos). Наблюдение реально охватило несколько календарных дней подряд (2026-08-25 → 2026-08-27) на реальном iPhone, без единого принудительного закрытия приложения свайпом за всё это время — ровно тот сценарий, который требовался.

## 2. Что было изменено

Плана 68-01:
- Снята постоянная блокировка `hasSyncedRef` в `lib/hooks/useHealthKitSync.ts` (гипотеза 1) — подтверждена прямым чтением кода при research: импорт глюкозы не выполнялся, если профиль Convex догружался после первого рендера, и ref навсегда запирал эффект.
- Добавлена ре-синхронизация по `AppState` (гипотеза 2) — теперь синхронизация запускается заново при каждом возврате приложения из фона, а не один раз за время жизни компонента.
- Добавлен троттлинг не чаще раза в 5 минут — защита от чрезмерно частых синхронизаций при быстром сворачивании/разворачивании.
- Добавлен диагностический след (`lib/health/logHealthKitSync.ts`): каждая попытка синхронизации пишет `count` и `latestDate`/`latestRecordedAt` для движения и глюкозы, плюс `skipped-throttle`, когда синхронизация пропущена из-за троттлинга.

## 3. Наблюдения

Данные из диагностического следа (`[healthkit] ...` в консоли Metro), собранные на реальном устройстве за несколько дней без принудительного закрытия приложения:

```
[healthkit] movement-fetched {"count": 8, "latestDate": "2026-08-25"}
...
[healthkit] movement-fetched {"count": 9, "latestDate": "2026-08-27"}

[healthkit] glucose-fetched {"count": 2, "latestRecordedAt": "2026-08-25T11:47:00.000Z"}
...
[healthkit] glucose-fetched {"count": 3, "latestRecordedAt": "2026-08-26T21:18:00.000Z"}
```

Движение: `count` выросло с 8 до 9, `latestDate` продвинулась с 25 на 27 августа — новые дни фактически подтягивались между сессиями без переустановки/принудительного закрытия.

Глюкоза: `count` выросло с 2 до 3, `latestRecordedAt` продвинулась на новую дату — новое измерение было подхвачено между сессиями.

В промежутках между этими точками неоднократно фиксировались `[healthkit] skipped-throttle {"msSinceLast": ...}` — подтверждает, что 5-минутный троттлинг работает как задумано (не спамит синхронизацией при частом сворачивании/разворачивании).

Пользователь подтвердил результат явно: **Вариант А** (полный успех).

## 4. Вердикт по гипотезе 3

**Не воспроизводится.**

Апстрим issue `kingstinct/react-native-healthkit#330` описывает устаревание данных внутри нативного модуля — симптом, при котором JS запрашивает новые данные, но нативный слой отдаёт кэшированные старые значения, требуя принудительного закрытия приложения. На этом проекте, после снятия ref-блокировки и добавления `AppState`-ре-синхронизации, новые данные (и по движению, и по глюкозе) фактически появлялись между сессиями без единого принудительного закрытия — то есть внешнее ограничение, описанное в issue #330, здесь не проявилось.

Версии, на которых проверено: `@kingstinct/react-native-healthkit@14.0.2`, React Native `0.81.5`, Expo SDK `54`. Это отличается от версий из апстрим-репорта (`13.2.3` / RN `0.83.2` / SDK `55`) — возможно, проблема специфична для более новых версий библиотеки/RN, либо была исправлена между `13.2.3` и `14.0.2`, либо никогда не проявлялась на данной комбинации API HealthKit, используемых в этом проекте (`queryStatisticsCollectionForQuantity`, `queryQuantitySamples`). Это важно зафиксировать для будущего сопоставления, если проблема когда-либо проявится после обновления зависимостей.

## 5. Что делать дальше

Поскольку гипотеза 3 не воспроизвелась — **HEALTH-01 закрыт целиком на JS-уровне**, отдельного плана B (фоновая синхронизация через `expo-task-manager`/`expo-background-fetch`) не требуется. Если проблема когда-либо вернётся (например, после обновления `@kingstinct/react-native-healthkit` или RN), первый шаг — свериться с текущим статусом issue #330 и повторить это же наблюдение (диагностический след в `logHealthKitSync.ts` уже в коде и не требует доработки для повторной диагностики).

Отдельно обнаружено и исправлено в ходе этой же проверки: HealthKit-импорт глюкозы игнорировал предпочитаемую пользователем единицу измерения и всегда тегировал показания как `mg/dL` — не связано напрямую с гипотезой устаревания данных, но напрямую влияло на воспринимаемую пользователем корректность синхронизации. Исправлено в `lib/health/healthKit.ts` через `getPreferredUnit()`.
