<objective>
Реализовать чистую функцию приблизительной оценки уровня глюкозы от съеденной еды (GLU-01) и автоматическую проверку её поведения.

Purpose: D-05: нужна модель точнее грубой эмпирики по сумме углеводов — с учётом гликемического индекса продукта и времени с последнего приёма пищи. Гликемического индекса в схеме нет и готового машиночитаемого источника GI не существует (проверено в RESEARCH.md), но проект уже хранит по каждому блюду разбивку углеводов `totalNutrients.carbs.{total, net, fiber, sugar}`, из которой строится прокси-GI: блюдо с высокой долей сахара и низкой долей клетчатки даёт более резкий подъём, чем блюдо с теми же общими углеводами, но высокой клетчаткой. Дальше применяется стандартная формула гликемической нагрузки `GL = GI * carbs / 100` и кривая подъёма/спада относительно момента приёма пищи. D-07: величина показывается как абсолютное значение в тех же единицах, что и реальные измерения пользователя, поэтому нужна база отсчёта.
Output: `lib/nutrition/estimateGlucoseFromMeals.ts` + `scripts/verifyGlucoseEstimate.ts` + npm-скрипт.

    **Экспортируемые константы** (собрать в один объект `export const GLUCOSE_ESTIMATE_CONSTANTS`, чтобы скрипт-проверка мог на них ссылаться и чтобы калибровка была в одном месте):

    **Алгоритм (вся внутренняя математика ведётся в ммоль/л, конвертация в целевые единицы — только на последнем шаге):**
    1. *Целевая единица (D-07: те же единицы, что у реальных измерений).* Взять `unit` показания с максимальным `recordedAt` среди `readings`, у которых `now - recordedAt <= UNIT_LOOKBACK_MS`. Если таких нет — `"mmol/L"` (совпадает с дефолтом экрана ручного ввода). Это решение планировщика по открытому вопросу RESEARCH.md о неоднозначности единиц: единой настройки в схеме нет, поэтому источником истины считается последнее реальное измерение.
    2. *База отсчёта.* Собрать показания с `context === "fasting"` или `context === "beforeMeal"` и `now - recordedAt <= BASELINE_LOOKBACK_MS`; каждое привести к ммоль/л (`unit === "mg/dL" ? value / MGDL_PER_MMOL : value`); взять среднее арифметическое. Если таких показаний нет — `BASELINE_MMOL`. Это решение планировщика по открытому вопросу RESEARCH.md о базе отсчёта: собственные данные пользователя приоритетнее популяционной константы, константа — только запасной вариант.
    3. *Вклад каждого блюда.* Пропустить блюдо без `totalNutrients` или с `carbs.total <= 0`. Иначе:
       `sugarRatio = carbs.sugar / Math.max(carbs.total, 1)`;
       `fiberRatio = carbs.fiber / Math.max(carbs.total, 1)`;
       `estimatedGI = clamp(GI_BASE + GI_SUGAR_WEIGHT * sugarRatio - GI_FIBER_WEIGHT * fiberRatio, GI_MIN, GI_MAX)`;
       `glycemicLoad = estimatedGI * carbs.total / 100`.
    4. *Временное окно.* `minutesSinceMeal = (now - _creationTime) / 60000`. Пропустить блюдо при `minutesSinceMeal < 0` или `minutesSinceMeal >= WINDOW_MINUTES`. Вес: при `minutesSinceMeal <= PEAK_MINUTES` — `minutesSinceMeal / PEAK_MINUTES` (линейный подъём к пику на 60-й минуте); иначе — `Math.max(0, 1 - (minutesSinceMeal - PEAK_MINUTES) / (WINDOW_MINUTES - PEAK_MINUTES))` (линейный спад к нулю на 180-й минуте). Вклад = `glycemicLoad * weight`.
    5. *Итог.* `loadSum = сумма вкладов`. Если `loadSum <= 0` — вернуть `null` (нечего показывать; UI в этом случае не рисует строку оценки). Иначе `valueMmol = baselineMmol + loadSum * MMOL_PER_GL_UNIT`.
    6. *Конвертация и округление.* Для `"mmol/L"` — округлить до одного знака после запятой (`Math.round(x * 10) / 10`); для `"mg/dL"` — `Math.round(valueMmol * MGDL_PER_MMOL)`. Вернуть `{ value, unit, mealCount }`, где `mealCount` — число блюд, давших ненулевой вклад.

    **Обязательный шапочный doc-комментарий на русском** (в стиле `convex/utils/localWeekBounds.ts`), явно фиксирующий: (а) `estimatedGI` — это прокси, а не настоящий гликемический индекс продукта, потому что GI нигде не хранится и машиночитаемого источника нет; (б) формула `GL = GI * carbs / 100` — стандартная и цитируемая, прокси-подстановка GI — нет; (в) константы кривой (пик 60 мин, возврат к базе 180 мин) — общие ориентиры, не клинические данные; (г) поэтому величина обязана подаваться в UI со знаком «≈» и никогда не выдаваться за измерение.

    **Что делать НЕ надо:** не писать оценку в таблицу `glucoseReadings` ни под каким `source` — это молча смешает оценку с измерениями во всех существующих запросах (недельные/месячные, PDF-отчёт в `convex/reports/`, экраны наблюдателя из Phase 6). Не переизобретать `isGlucoseOutOfRange` и `GLUCOSE_RANGES` — они уже есть в `thresholds.ts` и переиспользуются на месте отображения (план 68-05).
