From `convex/meals/getMeal.ts` (current, full file — change ONLY line 14):
```typescript
import { getAuthUserId } from "@convex-dev/auth/server";
import { query } from "../_generated/server";
import { v } from "convex/values";
import logError from "@/lib/utils/logError";

const getMeal = query({
  args: { mealId: v.id("meals") },
  handler: async (ctx, { mealId }) => {
    try {
      const userId = await getAuthUserId(ctx);
      if (userId === null) throw new Error("Unauthorized");

      const meal = await ctx.db.get(mealId);
      if (!meal || meal.status === "error" || meal.status === "deleted") {
        return null;
      }
      if (meal.userId !== userId) throw new Error("Forbidden");

      const mealItems = await ctx.db
        .query("mealItems")
        .withIndex("byMealId", (q) => q.eq("mealId", mealId))
        .collect();

      const mealItemsWithFood = await Promise.all(
        mealItems.map(async (mealItem) => {
          const food = await ctx.db.get(mealItem.foodId);
          return { ...mealItem, food };
        })
      );

      return { meal, mealItems: mealItemsWithFood };
    } catch (error) {
      logError("getMeal error", error);
      throw error;
    }
  },
});

export default getMeal;
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → confirmMeal | Fully client-controlled `items` array and `mealName`/`description` strings enter a public mutation — must be validated/clamped before persistence and before driving downstream AI/embedding fan-out |
| Client → retryProcessDetectedItems | Client controls only `mealId`; all other retry parameters (detectedItems, description, photoStorageId) are re-read from the already-persisted, already-validated `meals` row, not re-accepted from the client |
| confirmMeal/retryProcessDetectedItems → scheduler → processDetectedItemsAction | Scheduled call carries an explicit, mutation-validated `userId` — re-verified again inside updateMealInternal/replaceMealItemsInternal (plan 07-01) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-06 | Denial of Service (cost) | confirmMeal.ts | mitigate | Server-side `.slice(0, 30)` cap + `Math.max(1, Math.min(1500, ...))` grams clamp on the fully client-controlled `items` array, independent of any client-side validation — RESEARCH.md Assumption A2 |
| T-07-07 | Elevation of Privilege / Tampering | retryProcessDetectedItems.ts | mitigate | `meal.userId !== userId → Forbidden` ownership check AND `meal.status !== "error" → reject` — prevents retrying another user's meal or re-triggering AI spend on a meal that is not actually stuck |
| T-07-08 | Denial of Service (cost) / Repudiation of the 50/day contract | retryProcessDetectedItems.ts | mitigate | Dedicated `mealRetry` fixed-window bucket (10/hour, keyed by mealId, from plan 07-01) — closes RESEARCH.md Pitfall 5's uncounted-AI-call abuse surface (`selectCandidates`/`translateFood`/`calculateHealthScore` inside `processDetectedItems` are not covered by the 50/day `aiFeatures` limit and could otherwise be re-triggered unboundedly via retry) |
| T-07-09 | Information Disclosure | getMeal.ts, getWeekMeals.ts | accept | Removing the `status === "error"` filter exposes error-status meals through the SAME ownership-checked query path (`meal.userId !== userId → Forbidden` in getMeal is untouched; getWeekMeals is already scoped to `userId` via its index) — no new data becomes reachable by a non-owner, only previously-over-filtered own data becomes visible again |
</threat_model>
