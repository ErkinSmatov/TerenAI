# 01-03 SUMMARY — Раздел диагностики и локальная production-сборка

**Статус:** выполнено 2026-08-05

## Установленная версия

**`expo-application@~7.0.8`** — официальный модуль Expo без конфиг-плагина. Даёт `nativeApplicationVersion` и `nativeBuildVersion`, то есть реальные значения из собранного бинарника, а не из `app.config.ts`. Это принципиально: `eas.json` использует `appVersionSource: "remote"` с `autoIncrement`, номер сборки присваивает сервер EAS, и в исходниках его нет. `expo-constants` для этого не годится — нужные поля там помечены deprecated, а `@typescript-eslint/no-deprecated` включён в режиме `error`.

## Раздел диагностики

`components/settings/DiagnosticsSection.tsx`, подключён последним элементом в `app/app/(tabs)/settings.tsx`.

**Параметры скрытого триггера:**

| Параметр | Значение | Константа |
|---|---|---|
| Порог нажатий | 7 | `UNLOCK_TAPS` |
| Таймаут сброса счётчика | 3000 мс | `TAP_RESET_MS` |

Нажатия считаются по строке с версией. Если между нажатиями прошло больше `TAP_RESET_MS`, счётчик сбрасывается в единицу. До разблокировки дополнительные строки не рендерятся вовсе.

**Четыре действия после разблокировки:**

1. `Sentry.captureMessage` уровня `info` — базовая доставка, показывает Event ID
2. `Sentry.captureException` с новым `Error` — доставка исключений и читаемость стека (OBS-03), показывает Event ID
3. `logError(...)` — отдельно от предыдущего намеренно: проверяет цепочку `logError` → реестр репортеров → Sentry (OBS-02), а не прямой вызов SDK. Event ID недоступен, `logError` ничего не возвращает
4. `Sentry.nativeCrash()` — помечен `destructive`, закрыт подтверждающим `AlertDialog` по образцу удаления аккаунта

Строка с версией полезна и сама по себе: тестер может назвать точную сборку в баг-репорте.

## Скрипты в package.json

```
"env:pull:production": "eas env:pull --environment production --path .env.production.local"
"prebuild:prod":       "APP_VARIANT=production npx expo prebuild --clean"
"ios:prod":            "APP_VARIANT=production npx expo run:ios --configuration Release"
```

Существующие `env:pull`, `ios`, `eas:prod` не изменялись.

Отдельный файл `.env.production.local` вместо перезаписи `.env.local` — чтобы случайный запуск dev-режима после отладки не пошёл в production-конфигурации. Игнорирование git **проверено командой**, а не принято на веру: `git check-ignore -q .env.production.local` → код 0, покрывается шаблоном `.env*.local` (`.gitignore:36`).

## docs/PRODUCTION-DEBUGGING.md

Каталог `docs/` создан. Пять разделов: локальное воспроизведение production; сравнение трёх способов сборки; проверка отчётов через раздел диагностики; **где искать ошибки, не попадающие в Sentry**; ограничение цикла доставки из-за отсутствия OTA.

Два ручных шага вынесены явно, потому что оба дают тихий отказ:
- заменить `EXPO_PUBLIC_SENTRY_ENVIRONMENT` на `local-release` перед локальным прогоном, иначе события с машины разработчика смешаются с TestFlight-сборками
- экспортировать `SENTRY_AUTH_TOKEN` в окружение оболочки — это переменная времени сборки, Expo её в бандл не вшивает; без неё сборка не упадёт, но стек-трейсы останутся нечитаемыми

Секретов в файле нет, проверено grep-гейтом на `ingest.`.
