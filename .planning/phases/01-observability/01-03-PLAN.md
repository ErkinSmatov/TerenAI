## Как в этом проекте воспроизводится production локально

Из `CRASH-DIAGNOSIS.md` §3, проверено против конфигурации репозитория:

- `package.json` сегодня имеет единственный скрипт `env:pull`, жёстко привязанный к `--environment development`. Именно поэтому production-окружение ни разу не проверялось локально и пустая EAS-среда осталась незамеченной до краша 1.2.1 (1).
- Скрипт `ios` жёстко задаёт `APP_VARIANT=development`, то есть даёт bundle id `com.codetau.terenai.dev` — это не то, что уходит в TestFlight.
- Expo читает `.env` файлы в порядке приоритета `.env.<mode>.local` → `.env.local` → `.env.<mode>` → `.env`. При сборке в конфигурации Release режим — `production`, поэтому файл `.env.production.local` перекроет `.env.local`. Шаблон `.env*.local` уже присутствует в `.gitignore`, отдельная запись не нужна — но это надо проверить, а не предположить.
- Переменные с visibility `secret` в EAS **недоступны** при `eas build --local`; переменные `plaintext` и `sensitive` — доступны. Все переменные Sentry заведены как `plaintext`/`sensitive`, так что этот способ рабочий.

Установить `expo-application` командой `npx expo install expo-application`. Это официальный модуль Expo без конфиг-плагина; он даёт `nativeApplicationVersion` и `nativeBuildVersion` — реальные значения из собранного бинарника, а не из `app.config.ts`. Это важно, потому что `eas.json` использует `appVersionSource: "remote"` с `autoIncrement`: номер сборки присваивается сервером EAS и в исходниках его нет. Не использовать для этого `expo-constants` — соответствующие поля там помечены как deprecated, а `eslint.config.mjs` включает правило `@typescript-eslint/no-deprecated` в режиме `error`.

Создать `components/settings/DiagnosticsSection.tsx` — компонент без пропсов, экспорт по умолчанию, в стиле остальных файлов `components/settings/`.

Видимая часть: одна строка `SettingsItem` с текстом вида «TerenAI <nativeApplicationVersion> (<nativeBuildVersion>)» и подходящей иконкой из `lucide-react-native` (например `InfoIcon`). Эта строка полезна сама по себе: тестер может назвать точную сборку в баг-репорте.

Скрытый триггер: локальное состояние счётчика нажатий и метки времени последнего нажатия. Каждое нажатие по строке версии увеличивает счётчик; если между нажатиями прошло больше трёх секунд — счётчик сбрасывается в единицу. На седьмом нажатии выставляется состояние `unlocked`. Пока `unlocked` ложно, никаких дополнительных строк не рендерится. Порог в семь нажатий выбран, чтобы обычный тестер не открыл раздел случайно; секретом это не является и не должно им быть.

После разблокировки отрисовать четыре действия в отдельной `SettingsGroup`:

1. «Отправить тестовое сообщение» — вызывает `Sentry.captureMessage` со строкой, однозначно опознаваемой в дашборде (например `"TerenAI diagnostics: test message"`) и уровнем `info`. Полученный event id показать через `Alert.alert`, чтобы его можно было продиктовать.
2. «Отправить тестовую ошибку» — конструирует новый `Error` с распознаваемым текстом и передаёт его в `Sentry.captureException`. Event id так же показать в `Alert.alert`. Это событие проверяет читаемость стек-трейса: в Sentry оно обязано указывать на этот файл со строкой (OBS-03).
3. «Проверить logError» — вызывает `logError` из `@/lib/utils/logError` с коротким статическим сообщением и новым `Error`. Это отдельное действие от предыдущего намеренно: оно проверяет именно цепочку `logError → реестр репортеров → Sentry` из плана 01-02, то есть требование OBS-02, а не прямой вызов SDK. Показать `Alert.alert` с подтверждением отправки (`logError` ничего не возвращает, поэтому event id здесь недоступен).
4. «Нативный краш (приложение закроется)» — помечен как `destructive`, обёрнут в `AlertDialog` с подтверждением по образцу удаления аккаунта. По подтверждению вызывает `Sentry.nativeCrash()`. Приложение закроется; событие отправится при следующем запуске.

Соблюсти конвенции проекта: тип пропсов через `type` (не `interface`), стили через `StyleSheet.create` внизу файла, цвета через `getColor()`, тексты интерфейса на русском. Асинхронные обработчики в `onPress` оборачивать через `void`, как это уже сделано на экране настроек, иначе сработает правило `@typescript-eslint/no-misused-promises`.

Подключить компонент в `app/app/(tabs)/settings.tsx` последним элементом внутри `ScrollView`, после группы с кнопкой «Выйти». Больше ничего на этом экране не менять.

Раздел остаётся в приложении постоянно, а не удаляется после проверки. Обратное потребовало бы ещё одного цикла сборки и заливки, а сам раздел безвреден: он не читает и не показывает пользовательские данные, только шлёт синтетические события.

**Раздел 1. Как воспроизвести production локально.** Пошагово: выгрузить переменные (`npm run env:pull:production`), пересобрать нативный проект (`npm run prebuild:prod`), запустить в конфигурации Release (`npm run ios:prod`). Для каждого — когда он уместен.

**Раздел 3. Как проверить, что отчёты об ошибках работают.** Открыть настройки, семь раз нажать на строку с версией, выполнить четыре действия из раздела диагностики, найти события в Sentry.
