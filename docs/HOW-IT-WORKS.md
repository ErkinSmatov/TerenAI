# Как работает TerenAI

Полный цикл работы приложения: от запуска до появления калорий на главном экране. Документ описывает **логику и её причины**, а не пересказывает код построчно — код меняется, а решения и ограничения живут дольше.

Актуально на 2026-08-06.

---

## 1. Что делает приложение

Пользователь фотографирует еду — через несколько секунд видит калории и БЖУ.

Ключевая сложность, вокруг которой построена вся архитектура: **ИИ не знает точной пищевой ценности**. Он умеет распознать «жареная куриная грудка» на фото, но не может достоверно сказать, сколько в ней белка. Числа должны браться из проверенной базы — USDA FoodData Central.

Отсюда главная задача системы: **связать свободный текст от ИИ со структурированной записью в базе**. Этому посвящён весь пайплайн анализа.

---

## 2. Из чего собрано

| Слой | Технология | Где |
|---|---|---|
| Мобильное приложение | React Native 0.81 + Expo SDK 54, TypeScript | `app/`, `components/` |
| Навигация | Expo Router (файловая, как Next.js App Router) | `app/**/_layout.tsx` |
| Бэкенд | Convex — БД, серверные функции, реактивность, файловое хранилище | `convex/` |
| Распознавание и выбор | Grok 4.3 через OpenRouter | `convex/meals/analyze/` |
| Векторный поиск | Gemini `gemini-embedding-001`, 768 измерений | `searchFdcCandidates.ts` |
| База продуктов | USDA FDC + Open Food Facts | таблица `foods` |
| Подписки | RevenueCat (сейчас скрыты флагом) | `context/SubscriptionContext.tsx` |
| Диагностика | Sentry | `lib/monitoring/initMonitoring.ts` |

Язык один на обоих концах — TypeScript. Но серверный рантайм Convex это **V8-изолят, а не Node**: там нет `fs`, `process.argv` и пакетов с нативными модулями. Это ограничение регулярно всплывает в решениях ниже.

Клиент почти не содержит бизнес-логики. Он рисует интерфейс и вызывает функции Convex по имени через сгенерированный объект `api`. REST-эндпоинтов нет.

## 3. Запуск приложения

Порядок выполнения при старте задан жёстко в [index.ts](../index.ts):

```
1. react-native-get-random-values   — полифил криптографии
2. lib/monitoring/initMonitoring    — инициализация Sentry
3. expo-router/entry                — загрузка роутера и всего приложения
```

**Второй пункт обязан стоять выше третьего.** Роутер тянет `app/_layout.tsx` → `components/RootLayoutProvider.tsx`, а тот бросает исключение на уровне модуля, если не задан `EXPO_PUBLIC_CONVEX_URL`. Такое исключение происходит до первого рендера, и поймать его может только обработчик, установленный ещё раньше.

Это не теория: именно так умирала сборка 1.2.1 (1) — мгновенный вылет без единого следа в логах.

Сам модуль инициализации **не бросает исключений ни в одной ветке**. Если DSN отсутствует, он пишет предупреждение в консоль и молчит. Уронить приложение из-за отсутствия системы отчётов об ошибках означало бы повторить ту же ошибку, ради устранения которой он написан.

## 4. Авторизация и вход в приложение

### Развилка при старте

`app/_layout.tsx` делит приложение на три группы маршрутов:

```
app/        — основное приложение, только для авторизованных (<Stack.Protected>)
onboarding/ — доступен без авторизации
auth/       — только для НЕавторизованных
```

Дальше `app/app/_layout.tsx` уточняет: не авторизован → `/auth`, не прошёл онбординг → `/onboarding`, иначе показывает приложение.

### Три способа стать пользователем

Все три создают **настоящего пользователя Convex** с записью в таблице `users` и профилем в `profiles`:

| Провайдер | Когда |
|---|---|
| `Anonymous` | кнопка «Продолжить без аккаунта» в конце онбординга |
| `Google` | кнопка «Продолжить с Google» |
| `Apple` | кнопка есть, но ключи `AUTH_APPLE_*` не заведены — пока не работает |

Ключевое архитектурное решение: **гость — это полноценный `userId`, а не особый режим**. Благодаря этому 20 функций в `convex/`, гейтнутых через `getAuthUserId`, и вся защита маршрутов работают без единой правки, а данные гостя хранятся в тех же таблицах.

При создании любого пользователя срабатывает колбэк `afterUserCreatedOrUpdated` в [convex/auth.ts](../convex/auth.ts) и заводит профиль со значениями по умолчанию.

### Почему вход в конце онбординга

Пользователь сначала получает ценность — персональный план по калориям — и только потом ему предлагают аккаунт. Отказ ничего не блокирует.

Шаг `OnboardingCreateAccount` автоматически пропускается, если пользователь уже авторизован (`skip: ({ isAuthenticated }) => isAuthenticated`). Как только вход состоялся любым способом, `isAuthenticated` становится истинным, и онбординг сам перелистывает шаг — переключать его вручную не требуется.

## 5. Онбординг и расчёт целей

Четыре секции: `Основы` → `Цель` → `Программа` → `Результаты`.

Данные копятся в `OnboardingContext` **на клиенте** и сохраняются на сервер один раз, в самом конце, мутацией `completeOnboarding`. Поэтому прохождение онбординга не требует авторизации — она нужна только в момент сохранения.

Расчёт целей ([computeNutritionTargets.ts](../convex/nutrition/computeNutritionTargets.ts)) — чистая арифметика без ИИ:

```
возраст + пол + рост + вес
        ↓  computeBmr              базовый обмен
        ↓  getNeatMultiplier       коэффициент бытовой активности
        ↓  computeExerciseCalories расход на тренировки
        ↓  computeMaintenanceCalories  калории поддержания веса
        ↓  computeCalorieTarget    поправка на цель и темп изменения веса
        ↓  computeMacroTargets     разбивка на белки/жиры/углеводы
```

Результат — `targets` в профиле: калории и три макронутриента.

## 6. Анализ блюда — ядро приложения

Три входа ведут в один пайплайн: **фото**, **текстовое описание**, **штрихкод**.

### Общий каркас (фото и описание)

```
                    ┌─────────────────────────────────┐
   фото/описание →  │ 1. Grok: что это за блюдо?       │
                    │    → название + список           │
                    │      ингредиентов с граммовкой   │
                    └──────────────┬──────────────────┘
                                   ↓
                    ┌─────────────────────────────────┐
                    │ 2. Gemini: эмбеддинг названий    │
                    │    → векторный поиск по foods    │
                    │    → топ-3 кандидата на позицию  │
                    └──────────────┬──────────────────┘
                                   ↓
                    ┌─────────────────────────────────┐
                    │ 3. Grok: выбрать по одному       │
                    │    кандидату и уточнить граммы   │
                    └──────────────┬──────────────────┘
                                   ↓
                    ┌─────────────────────────────────┐
                    │ 4. Досбор данных и сохранение    │
                    └─────────────────────────────────┘
```

### Шаг 1 — распознавание

`detectMealItems` отдаёт модели фото и требует строгий JSON: название блюда по-русски и массив `{ name, grams }`.

Главное правило промпта — **разбирать составные блюда на компоненты**. Не «лазанья», а листы теста + фарш + томатный соус + моцарелла + рикотта. Причина в том, что база USDA хранит ингредиенты, а не рецепты: точность достигается сложением компонентов, а не поиском готового блюда.

Промпт также требует учитывать неочевидное — масло для жарки, панировку, соусы. Их часто нет на фото, но в калориях они весят много.

Если распознать не удалось, блюдо получает статус `error` и пайплайн останавливается.

### Шаг 2 — поиск кандидатов

Здесь решается главная задача системы: `"grilled chicken breast"` от модели нужно связать с записью базы `"Chicken, broiler, breast, meat only, cooked, grilled"`. Точное совпадение строк тут не работает.

[searchFdcCandidates.ts](../convex/meals/analyze/searchFdcCandidates.ts) превращает названия в векторы через `gemini-embedding-001` и ищет ближайшие записи векторным индексом Convex. Берётся вдвое больше кандидатов, чем нужно, затем сортировка по близости и обрезка до трёх.

Две детали, от которых зависит качество поиска:

- **Асимметричные типы задач.** Продукты в базе эмбеддятся с `RETRIEVAL_DOCUMENT`, а поисковые запросы — с `RETRIEVAL_QUERY`. Gemini строит для них разные представления; перепутать их — типичная ошибка, тихо ухудшающая результат.
- **Нормализация.** Оба пути прогоняются через `l2Normalize`, что позволяет сравнивать векторы скалярным произведением.

Эмбеддинги продуктов считаются заранее, фоновым скриптом [backfillFoodEmbeddings.ts](../convex/utils/backfillFoodEmbeddings.ts), а не в момент запроса.

### Шаг 3 — выбор

Модель снова получает фото, свой же список из шага 1 и три кандидата на каждую позицию с их макросами на 100 г. Задача: выбрать по одному `fdcId` и при необходимости поправить граммовку.

Требование промпта — **не выбирать составные продукты**, которые задублируют другие позиции. Если в списке уже есть отдельно курица, отдельно панировка и отдельно масло, то кандидат «жареная курица в панировке» посчитает то же самое дважды.

Страховка на случай, если модель пропустит позицию: `ensureSelections` подставляет ближайшего по вектору кандидата. Лучше приблизительный результат, чем потерянный ингредиент.

### Шаг 4 — досбор и сохранение

Для каждого выбранного продукта [processDetectedItems.ts](../convex/meals/analyze/processDetectedItems.ts):

1. **Перевод названия на русский** — если его ещё нет. Отдельный вызов ИИ.
2. **Оценка полезности** (`healthScore`) — если её ещё нет. Тоже вызов ИИ.
3. Запись позиции блюда.

Оба обогащения выполняются **один раз на продукт и кэшируются в общей таблице `foods`**. Таблица общая для всех пользователей, поэтому чем дольше живёт приложение, тем реже нужны эти вызовы: популярные продукты уже переведены и оценены.

Наконец `replaceMealItems` сохраняет позиции, а `updateMealTotals` считает суммы.

### Штрихкод — короткий путь

Отдельный маршрут: продукт ищется в Open Food Facts по коду, при необходимости добавляется в `foods` и сразу становится позицией блюда. Ни распознавания, ни векторного поиска — данные уже структурированы.

### Статусы блюда

```
pending → processing → done
                    ↘ error
                      deleted (мягкое удаление)
```

Блюдо создаётся со статусом `processing` **до** обращения к ИИ. Благодаря реактивности Convex пользователь сразу видит карточку в состоянии загрузки, а не пустой экран на несколько секунд.

Обработчик ошибок помечает блюдо как `error` — но сам обёрнут в отдельный `try/catch`: сбой при записи ошибки не должен затирать исходную причину.

## 7. Расчёт калорий

Числа хранятся **в пересчёте на 100 г** (`macrosPer100g`, `microsPer100g`, `nutrientsPer100g`), а вес позиции — отдельным полем.

[updateMealTotals.ts](../convex/meals/updateMealTotals.ts) складывает позиции пропорционально весу:

```
ratio = граммы / 100
калории += калории_на_100г × ratio
```

Отдельного внимания заслуживает **оценка полезности блюда**. Она считается не средним арифметическим, а средним, взвешенным по калорийности:

```
score = Σ(score_позиции × калории_позиции) / общие_калории
```

Иначе щепотка петрушки влияла бы на оценку так же сильно, как основное блюдо.

## 8. Лимиты и стоимость

Одно блюдо — это **три-четыре вызова ИИ** (распознавание, выбор, плюс перевод и оценка полезности для новых продуктов) и один вызов эмбеддингов.

Защита — `@convex-dev/rate-limiter`: **50 AI-запросов на пользователя в сутки**, общий бюджет на все функции. Не зависит от подписки и продолжает действовать при выключенной монетизации.

Оплата раздельная и это важно при отладке:

| Что | Через кого | Ключ |
|---|---|---|
| Grok 4.3 (распознавание, выбор, перевод) | OpenRouter | `OPENROUTER_API_KEY` |
| Gemini (эмбеддинги) | Google напрямую | `GOOGLE_GENERATIVE_AI_API_KEY` |

Если анализ падает — смотреть, на каком шаге: распознавание и выбор упрутся в OpenRouter, векторный поиск в Google.

## 9. Подписка

Сейчас **выключена одним флагом** — `isMonetizationEnabled: false` в [config/subscriptionConfig.ts](../config/subscriptionConfig.ts). Все функции доступны всем.

Гейты стояли в двух слоях, и снимать нужно было оба:

- **клиент** — теперь проверяет `hasProAccess`, а не `isPro`;
- **сервер** — три действия в `convex/meals/analyze/` бросали `Pro subscription required`.

Спрятать только интерфейс было бы хуже, чем не трогать вовсе: кнопка стала бы доступной, а анализ падал бы с ошибкой уже после съёмки.

`isPro` при этом сохранил честный смысл — это реальный статус в RevenueCat. Возврат монетизации: поменять флаг и выполнить `npx convex dev --once`.

## 10. Наблюдаемость

`logError(message, error)` вызывается из **сорока мест в трёх несовместимых средах**: клиент React Native, изолят Convex и Node-скрипты импорта базы.

SDK Sentry невозможно загрузить в Convex, поэтому прямой импорт сломал бы бэкенд. Решение — **реестр репортеров**: [lib/utils/errorReporter.ts](../lib/utils/errorReporter.ts) не имеет ни одного импорта, а приёмник регистрирует только клиент при старте. В Convex и скриптах он остаётся `null`, и поведение там не изменилось.

**Что в Sentry не попадёт:**

- ошибки функций Convex — искать в `npx convex logs`;
- краши до загрузки JS-бандла — Xcode Organizer;
- всё, что происходит в dev (`enabled: !__DEV__`).

Подробности и проверка — [PRODUCTION-DEBUGGING.md](./PRODUCTION-DEBUGGING.md).

## 11. Сборка и доставка

Нативные папки `ios/` и `android/` **не хранятся в git** — они генерируются из `app.config.ts` при сборке. Правки плагинов применяются на сервере EAS автоматически.

Переменные разделены по назначению:

| Куда | Что | Как задаётся |
|---|---|---|
| EAS | `EXPO_PUBLIC_*` — попадают в клиентский бандл | `eas env:set` |
| EAS | `SENTRY_AUTH_TOKEN` — нужен сборщику | `eas env:set --visibility sensitive` |
| Convex | серверные секреты: ключи ИИ, OAuth, JWT | `npx convex env set` |

**Переменные с префиксом `EXPO_PUBLIC_` вшиваются в бинарник в момент компиляции.** Задать их задним числом и переустановить старую сборку недостаточно — нужна новая сборка.

OTA-обновлений нет: `expo-updates` не установлен, поэтому правка даже в одну строку JS требует полного цикла сборки и заливки. Это запланировано к изменению.

## 12. Известные ограничения

| Ограничение | Следствие |
|---|---|
| Вход через Apple не работает | ключи `AUTH_APPLE_*` не заведены; блокирует релиз в App Store |
| Сборки ходят в dev-деплоймент Convex | данные тестеров смешаны с данными разработки |
| Нет вебхука RevenueCat | статус подписки обновляется только когда клиент сам его запросит |
| Нет автотестов | ни одного; проверка — `npm run tsc`, `npm run lint` и ручной прогон |
| Локаль продуктов зашита как `ru` | `lib/off/fetchProduct.ts` игнорирует переданный параметр |
| Нет OTA | цикл исправления — 30–45 минут |
