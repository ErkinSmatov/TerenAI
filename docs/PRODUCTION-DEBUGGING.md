# Отладка production-сборки TerenAI

Как воспроизвести поведение релизной сборки локально, как проверить, что отчёты об ошибках доходят, и — не менее важно — где искать ошибки, которые в Sentry **не попадут**.

Инструкция рассчитана на человека, который не участвовал в настройке.

---

## 1. Как воспроизвести production локально

```bash
npm run env:pull:production   # выгрузить переменные окружения production из EAS
npm run prebuild:prod         # пересобрать нативный проект с конфиг-плагинами
npm run ios:prod              # запустить в конфигурации Release
```

**Зачем `prebuild:prod`.** Локальные `ios/` и `android/` на диске могли быть сгенерированы до подключения конфиг-плагина Sentry. Без пересборки нативная часть SDK в приложение не попадёт, и события будут теряться без всякого сообщения об ошибке.

**Отдельный файл переменных.** `env:pull:production` пишет в `.env.production.local`, а не перезаписывает `.env.local`. Это сделано намеренно: иначе следующий запуск в dev-режиме молча ушёл бы в production-конфигурацию. Expo читает `.env` файлы по приоритету `.env.<mode>.local` → `.env.local` → `.env.<mode>` → `.env`, а сборка в конфигурации Release использует режим `production`. Файл покрыт шаблоном `.env*.local` в `.gitignore`.

### Две вещи, которые нужно сделать вручную

**Поменять метку окружения.** Выгруженный файл содержит `EXPO_PUBLIC_SENTRY_ENVIRONMENT=testflight`. Перед локальным прогоном замените значение на `local-release` — иначе события с вашей машины смешаются в дашборде с событиями настоящих TestFlight-сборок, и статистика «сколько запусков закончилось крашем» перестанет что-либо значить.

**Экспортировать токен для sourcemaps.** `SENTRY_AUTH_TOKEN` попадёт в `.env.production.local`, но это переменная **времени сборки**, а не рантайма приложения — Expo её в бандл не вшивает. Чтобы sourcemaps загрузились при локальной release-сборке, токен должен быть в окружении оболочки:

```bash
export SENTRY_AUTH_TOKEN=$(grep '^SENTRY_AUTH_TOKEN=' .env.production.local | cut -d= -f2-)
npm run ios:prod
```

Без этого сборка не упадёт — просто стек-трейсы останутся нечитаемыми.

## 2. Три способа воспроизведения и когда какой уместен

| Способ | Точность | Скорость | Переменные окружения |
|---|---|---|---|
| `eas build --profile production --local` | наивысшая — та же последовательность, что на сервере | самый медленный | из EAS, кроме visibility `secret` |
| Release-схема в Xcode | высокая | средняя | подключаются вручную в схеме |
| `npm run ios:prod` | достаточная для JS-уровня | самый быстрый цикл | из `.env.production.local` |

**Что выбирать.** Для проверки JS-логики, инициализации и доставки событий — третий способ, он окупается скоростью. Для отладки с точками останова в нативном коде — Xcode. Для проверки самой процедуры сборки перед важным релизом — первый.

Все переменные Sentry в этом проекте заведены с visibility `plaintext` и `sensitive`, поэтому доступны во всех трёх вариантах. Ограничение на `secret` здесь не мешает.

## 3. Как проверить, что отчёты об ошибках работают

В приложении есть встроенный раздел диагностики — он позволяет проверить Sentry **из уже установленной сборки, без пересборки**.

1. Открыть `Настройки`
2. Семь раз нажать на строку с версией внизу экрана (между нажатиями не больше трёх секунд, иначе счётчик сбрасывается)
3. Появится группа из четырёх действий

| Действие | Что проверяет |
|---|---|
| Отправить тестовое сообщение | базовую доставку событий |
| Отправить тестовую ошибку | доставку исключений и читаемость стек-трейса |
| Проверить logError | цепочку `logError` → реестр репортеров → Sentry |
| Нативный краш | нативный слой; событие уйдёт при следующем запуске |

Первые три показывают Event ID в диалоге — по нему событие ищется в дашборде.

**Что смотреть в событии Sentry:**

- стек-трейс указывает на файл `.ts`/`.tsx` с номером строки, а не на адреса Hermes-байткода — значит sourcemaps загрузились
- `release` вида `com.codetau.terenai@<version>+<build>`
- окружение соответствует ожидаемому (`testflight` для TestFlight-сборок, `local-release` для локальных)
- платформа и версия сборки заполнены

## 4. Где искать ошибки, которые НЕ попадают в Sentry

Самый важный раздел для будущей отладки. Отсутствие события в Sentry не означает, что ошибки не было.

### Ошибки Convex-функций

**В Sentry их нет и не будет.** Серверный рантайм Convex — это V8-изолят, куда SDK React Native физически не может быть загружен. Репортер там не регистрируется по устройству, а не по недосмотру.

Такие ошибки по-прежнему пишутся через `logError` в `console.error` и видны в логах деплоймента:

```bash
npx convex logs
```

либо в дашборде Convex, вкладка `Logs`.

**Важно:** TestFlight-сборки текущего майлстоуна ходят в **dev**-деплоймент `keen-meerkat-110` (решение зафиксировано в `.planning/PROJECT.md`). Серверные логи тестовых сборок искать именно там, а не в прод-деплойменте.

*Возможное развитие:* у Convex есть собственная интеграция отправки исключений в Sentry, настраиваемая в дашборде деплоймента. В объём этой фазы она не входила, доступность на текущем тарифе не проверялась.

### Краши до загрузки JS-бандла

Не покрыты. Опция `useNativeInit` не включалась — она требует правки AppDelegate и отдельного файла `sentry.options.json` с DSN в корне проекта. Решение и его последствия зафиксированы в `.planning/phases/01-observability/01-02-SUMMARY.md`.

Такие краши ищутся через Xcode Organizer (`Window` → `Organizer` → `Crashes`) или в App Store Connect.

### События в dev-режиме

Отправка отключена намеренно: `enabled: !__DEV__`. В dev-клиенте ошибки видны в консоли Metro, засорять ими проект Sentry смысла нет. Локальная Release-сборка даёт `__DEV__ === false`, поэтому проверка по разделу 3 работает.

## 5. Ограничение цикла доставки

`expo-updates` в проекте не установлен — **OTA-обновлений нет**. Любая правка JS, даже в одну строку, требует полной пересборки EAS и повторной заливки: примерно 30–45 минут на цикл.

Отсюда два следствия для отладки:

- раздел диагностики встроен в приложение постоянно, а не удаляется после проверки
- локальную Release-сборку из раздела 1 стоит использовать до того, как запускать сборку EAS: ошибку дешевле поймать за минуты, чем за час

Снятие этого ограничения запланировано как Phase 5 роадмапа (EAS Update).
